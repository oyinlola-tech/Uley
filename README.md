# Uley student accommodation platform

Uley helps students discover verified off-campus accommodation, compare options, request inspections before applying, and report housing issues. Landlords and explicitly assigned caretakers manage property requests; school administrators provide verification and escalation oversight.

## Repository apps

- `apps/web` — Next.js landing, onboarding, and account pages.
- `apps/mobile` — Expo app with a three-screen illustrated introduction, student/landlord/caretaker registration, sign-in, recovery, and account security screens.
- Root — Fastify API, Prisma/PostgreSQL persistence, and auth services.

## Local setup

1. Install root dependencies with `npm install` and copy `.env.example` to `.env`.
2. Set a random `ACCESS_TOKEN_SECRET` of at least 32 characters and configure `DATABASE_URL` for PostgreSQL.
3. Generate Prisma Client and sync the database directly from `schema.prisma` with `npm run prisma:generate` and `npm run prisma:db:push`.
4. Start the API with `npm run dev` (default port `3001` when configured in `.env`).
5. Start the web app with `cd apps/web && npm install && npm run dev`; open `http://localhost:3000`.
6. Start the mobile app with `cd apps/mobile && npm install && npm run start`.

For a physical phone, set `EXPO_PUBLIC_API_BASE_URL` to the API computer's LAN address, such as `http://192.168.1.20:3001/api/v1`. Use HTTPS for hosted environments.

## Authentication

The API supports student, landlord, and caretaker registration, sign-in, refresh-token rotation, sign-out, sign-out from all sessions, current-account lookup, authenticated password changes, and one-time email-code password recovery. Browser sessions use an HTTP-only refresh cookie; native sessions keep the refresh token in SecureStore. Password recovery requires SMTP in production. Without SMTP in development, the recovery code is printed to the API terminal.

## University coverage

Student and landlord registration list federal and state universities from a static snapshot of the National Universities Commission's Nigerian University System directory: 77 federal and 69 state institutions at the time it was sourced. Private universities are excluded from the public selector. OAUSTECH remains marked as the first pilot institution. The seed refreshes this public directory from `src/constants/nigerianPublicUniversities.constant.ts`; check the [NUC directory](https://enuc.nuc.edu.ng/nus) and refresh the snapshot when its ownership or institution listings change.

If a university is missing, the registration form lets the user provide its name, campus city, and state. Uley saves that university as an inactive, unclassified request and still creates the account. Users can browse by current device location using the “Find homes near me” control without a listed university; the 10 km radius search does not require a campus record. Every property inherits its landlord's university association.

## Landlord property verification

Landlords can request school verification from `/landlord` on web or mobile. After approval, they save a property draft with an available unit, upload at least one photo, then submit the package for school review. School staff review landlord and property requests at `/admin/reviews`; rejected requests require a reason, and approved properties become public in `/listings`. The API protects these routes by account role. Landlords can assign a registered caretaker to each property by account email and remove access from the same property card. Caretakers see and respond to complaints only for currently assigned properties; the property relationship is checked on every complaint and evidence request. Students can still send urgent cases directly to school staff, and assigned caretakers receive in-app alerts for new complaints. Caretaker registration does not require university selection. Landlord identity evidence is reviewed through the school's existing process; this release does not upload identity documents.

### Private image safety service

Property photo uploads retry failed chunks and resume missing chunks for up to 24 hours. Local storage uses 1 MiB parts; S3 mode uses 5 MiB parts so non-final multipart parts meet S3 requirements. In S3 mode, Prisma stores upload ownership and expiry metadata while FastAPI manages provider multipart IDs and parts, so any API instance can accept the next chunk. After transfer, the API stores a Prisma scan job and temporarily stores its bounded source bytes in PostgreSQL until the scan completes. Multiple API instances can claim jobs using expiring leases; failed scanner calls retry with backoff, while rejected and exhausted jobs expose a terminal status through the authenticated upload-status endpoint. Browser and mobile clients poll that status and retain their device copy until scanning succeeds. Community ads accept one image up to 10 MB through `/api/v1/ads/:advertisementId/image`. For housing complaints, the reporting student can upload up to three MP4 videos, each at most 20 MB and 90 seconds, from web or mobile. FastAPI scans the original and normalized video with ClamAV, strips embedded metadata while re-encoding, generates a WebP poster, then stores the video and poster privately. Complaint media URLs are short-lived and only attached to complaint records the student, property landlord, or authorized school staff can access. The school reviews complaint evidence as part of its case workflow; malware scanning does not decide what a video depicts. Keep `MEDIA_UPLOAD_TEMP_DIRECTORY` (default `.data/media-uploads`) on persistent storage for local mode; local upload sessions remain single-node. For horizontal scaling, set `MEDIA_STORAGE_BACKEND=s3` in both the API and media service and configure the private bucket credentials. Apply an S3 lifecycle rule to abort incomplete multipart uploads and expire temporary `upload-sessions/` objects after two days. Push the Prisma schema before enabling S3 mode so session metadata can be stored. The pilot defaults to persistent local file storage using the Docker `media_files` volume. Set `MEDIA_SERVICE_API_KEY` to a unique random secret of at least 32 characters and start FastAPI plus ClamAV from the repository root with `docker compose -f docker-compose.media.yml up -d --build`; the image installs FFmpeg/ffprobe for video validation and normalization. The API reaches FastAPI at `MEDIA_SERVICE_URL` (default `http://localhost:8020`). Set `MEDIA_PUBLIC_BASE_URL` to a URL reachable by clients (for a phone on the LAN, use the development computer's LAN address). Local media storage is intended for development and a single-node pilot; use private S3-compatible storage before horizontal scaling. To switch, set `MEDIA_STORAGE_BACKEND=s3` and configure `MEDIA_S3_BUCKET`, `MEDIA_S3_REGION`, `MEDIA_S3_ENDPOINT_URL` (when required), `MEDIA_S3_ACCESS_KEY_ID`, and `MEDIA_S3_SECRET_ACCESS_KEY`. Property photos, ad images, and complaint evidence stay private and use expiring signed URLs. Readiness at `/health/ready` stays unavailable until ClamAV and the selected storage backend both respond.

For local Python development, install FFmpeg/ffprobe and ClamAV, then use `cd apps/media && python3 -m venv .venv && . .venv/bin/activate && pip install -e . && python -m src.main`. Configure the same `MEDIA_*` variables before starting. FastAPI requires reachable ClamAV and fails closed if the scanner or selected storage backend is unavailable. Automated image and video scanning checks file safety only. School moderators review ad content and decide property and landlord authenticity.

To provision the public university directory and first super administrator, set `SUPER_ADMIN_EMAIL`, `SUPER_ADMIN_NAME`, and a unique `SUPER_ADMIN_PASSWORD` of at least 16 characters in your private `.env` file. After configuring the database, run `npm run prisma:db:push`, then run `npm run prisma:seed`. The seed refreshes the 146 federal/state directory records and creates the super admin only when that email does not exist; it never resets an existing password. If that email already belongs to a non-super-admin account, seeding fails without changing it. Keep the password private and remove it from `.env` after provisioning.

## Property inspections

Students can request an inspection for an available unit on a published, approved property. They can view their requests at `/inspections` on web or mobile. Landlords can review requests and confirm or decline them at `/landlord/inspections` on web or `/inspections` on mobile. The API exposes `POST` and `GET /api/v1/inspections`, plus `GET /api/v1/landlord/inspections` and `POST /api/v1/landlord/inspections/:inspectionId/respond`.

## Rental applications

After a completed inspection, a student who recorded that they are interested or need follow-up can apply for that specific unit from the inspection record. Students track their applications at `/applications`; landlords review them at `/landlord/applications` on web and the corresponding student and landlord application screens on mobile. An application includes the inspection, the student’s optional move-in date and note, and the landlord’s response. Students can withdraw applications while they are submitted or under review. Landlords can mark an application under review, approve it, or decline it, with in-app notifications sent for each decision.

Approval reserves the unit and creates a requested occupancy. It does not claim the student has moved in: the landlord must still confirm occupancy through the existing move-in workflow, and any payment confirmation remains a separate explicit landlord action. If that move-in is declined, the application is declined and the available unit can appear in search again. Search and property detail exclude units with a pending/active occupancy or an approved application. Rental amounts retain the listing’s stated period (year, month, week, day, or night); the application screen also shows the inspection fee and deposit separately. API routes are `GET/POST /api/v1/applications`, `POST /api/v1/applications/:applicationId/withdraw`, `GET /api/v1/landlord/applications`, and `POST /api/v1/landlord/applications/:applicationId/respond`.

Occupancy-based housing complaints are available at `/complaints` (student), `/landlord/complaints`, `/caretaker/complaints`, and `/admin/complaints` on web; mobile uses `/complaints`, `/landlord-complaints`, `/caretaker-complaints`, and the admin complaint queue. A student needs an active confirmed occupancy to open a case. Normal cases go to the landlord first; urgent cases notify school support immediately, and students can escalate unresolved cases. Landlord/school status changes, complaint messages, and notifications commit transactionally; student confirmation is required to close a resolved case. Students can attach up to three scanned MP4 evidence videos per open case (20 MB and 90 seconds per clip); the web and mobile complaint views play signed, access-controlled clips with generated poster previews. Routes include `GET/POST /api/v1/complaints`, `GET /api/v1/landlord/complaints`, and `GET /api/v1/admin/complaints`; video upload is `POST /api/v1/complaints/:complaintId/videos` and is limited to the student who opened the complaint. Other actions are scoped to the student, property landlord, an actively assigned caretaker, or approved school safety roles. Landlords can assign registered caretakers from each property card; caretakers only receive cases and evidence for that property, and removal immediately revokes that scope. Nearby search is available on web and mobile: students explicitly share a one-time device location, choose a 10 km radius, and receive distance labels. Landlords can capture a property pin while on site. Public listing payloads omit exact property coordinates. Confirmed inspections also support opt-in location sharing: the student starts/stops sharing, their participant landlord can view the last point, updates refresh about every 8–10 seconds, and the database keeps only one point. Inactive points expire on read after two minutes. The current radius calculation uses Prisma bounding-box candidates and an in-process distance filter; use a spatial database/index strategy before large-scale geographic search.

## Sponsored campaigns and chat safeguards

Sponsored campaigns show a live listing-card preview before submission. School approval is required before landlords can pay for approved campaigns; one checkout can include up to ten campaigns. Set `BACHS_API_KEY` and `BACHS_WEBHOOK_SECRET`; optionally set `BACHS_API_BASE_URL` to `https://sandbox-api.bachs.io/v1` for sandbox or `https://api.bachs.io/v1` for production. Configure a Bachs webhook for `collection.succeeded` at `https://<api-host>/api/v1/payments/bachs/webhook`. Checkout initialization and status retrieval run on the API; signed, timestamp-checked Bachs webhook deliveries are checked against the stored session, exact NGN amount, and currency before campaigns activate. Campaigns are reserved to one pending checkout, and an expired checkout can be verified before it is released. A browser return alone never activates payment. Bachs requires public callback URLs, so local development omits callbacks while API status retrieval and webhooks continue to work. Apply the expanded Prisma schema with `npm run prisma:db:push` after configuring the database.

Messaging accepts up to 20 messages per user per rolling minute, with a Fastify request limit and a database-backed count. New conversations are limited to ten per user per minute; starting a flatmate conversation also has a 30-second cooldown and a four-per-ten-minute ceiling. Flatmate posts are limited to three per user per 30 minutes. Fastify's request limiter uses a per-process store in this setup; configure a shared rate-limit store before horizontally scaling the API. Database-backed rolling checks and forum cooldowns persist across API instances. The web and mobile inboxes use authenticated WebSockets at `/api/v1/conversations/live`; PostgreSQL `LISTEN/NOTIFY` fans out small message-available events across API instances only after an approved message commits. Clients fetch message contents through the participant-checked API, reconnect automatically, and refresh message history every 15 seconds while realtime is unavailable. Configure the production ingress to pass WebSocket upgrades over TLS, and keep the PostgreSQL listener connection limit in mind when sizing API instances.

## School administration

School staff use `/admin` on web or the mobile app for live account, listing, verification, inspection, and report totals plus the recent admin action log. The workspace has separate verification, inspection, complaint, report, listing, account, and super-admin staff screens. The super admin can create scoped staff accounts from `/admin/staff`; available roles are school administrator, verification administrator, safety administrator, inspection administrator, and account administrator. Each role has access only to its relevant dashboard tools, while school administrators retain full operational access. Super admins can suspend or restore staff accounts; suspensions revoke active sessions and all staff changes are audited. Rental application submission, review, approval, decline, withdrawal, and resulting move-in confirmation are recorded in the super-admin system log with the actor, target record, and state transition. Students can report a published listing from the web or mobile listing screen; reports require sign-in and are rate limited.

Super admins can open `/admin/logs` on web or mobile to search and paginate administrator actions, property-report submissions and decisions, housing complaint workflow and property-caretaker assignment events, denied requests, and unexpected API failures. `/api/v1/admin/logs` is restricted to `SUPER_ADMIN`. Each response includes an `x-request-id`; server errors also include the reference ID in the response body. Use that ID to match a student or staff error with the request failure event and API server log. The event log intentionally excludes request bodies, report descriptions, passwords, and tokens.
